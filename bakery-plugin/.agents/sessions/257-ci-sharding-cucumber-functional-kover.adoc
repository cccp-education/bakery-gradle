* Disjoint/exhaustif : **71/71** (vérifié `comm`), filtre agrégat `not @personal`
  (seule exclusion réellement appliquée par l'agrégat `bakery.scenarios.CucumberTestRunner`).
* `36_pipeline_contracts.feature` (seule feature `@pipeline-contracts`) est dans

  `bakery.scenarios,contracts.pipeline.scenarios` (ses steps vivent côté

* Tâches Gradle `cucumberTestShard{JbakeCore,LensTree,LangSwitch,I18nMassPipeline}`
  (spec `CucumberTaskSpec` + `registerCucumberTask`, mirror du classpath `cucumberTest`).

=== 2. Shards functionalTest (2)

`functionalTestShardA` (16 classes / ~84 tests) + `functionalTestShardB`
(12 classes / ~83 tests) via `filter { includeTestsMatching("bakery.X") }`.
**28/28** classes partitionnées (exhaustif/disjoint, vérifié).

*Découverte de la 1re itération* : la partition initiale ne listait que les 23
`*FunctionalTest.kt` ; **5 classes de test** du source set fonctionnel ne
respectent pas ce motif (`*FunctionalTests`, `ArchitectureValidationTest`) et
étaient silencieusement perdues → couverture fusionnée **80,81 %** (< 85 %). Le
correctif liste les **28** classes (`@Test` présent) et la garde détecte désormais
toute classe `@Test` non couverte.

=== 3. Garde anti « test fantôme »

`bakery.ci.BakeryCucumberShardCoverageTest` (patron S-269
`CodebaseCucumberShardCoverageTest`), parsing statique des sources :
. partition Cucumber disjointe et exhaustive des 71 features + filtre
  `not @personal` ;
. chaque runner enregistré comme tâche Gradle **et** invoqué par le workflow ;
. partition fonctionnelle disjointe/exhaustive des 28 classes `@Test` + les 2
  shards invoqués par le workflow ;
. le job `unit` exécute le `test` nu.

=== 4. Fusion kover inter-jobs

Chaque job téléverse `bakery-plugin/build/kover/bin-reports/*.ic`
(`actions/upload-artifact@v4`, `if-no-files-found: error`). Le job `coverage`
(`needs: [unit, functional-shard, bdd-shard, e2e]`) les télécharge tous
(`actions/download-artifact@v4`, `pattern: kover-ic-*`, `merge-multiple: true`)
dans `build/kover/bin-reports/`, puis :

[source,bash]
----
./gradlew koverXmlReport koverThresholdCheck \
  -x test -x functionalTest -x cucumberTest -x e2eTest -x nodeTest \
  -x functionalTestShardA -x functionalTestShardB \
  -x cucumberTestShardJbakeCore -x cucumberTestShardLensTree \
  -x cucumberTestShardLangSwitch -x cucumberTestShardI18nMassPipeline
----

* **Mécanisme validé localement** (report-only, zéro test) : `koverXmlReport`
  agrège les `.ic` présents même quand la tâche est `-x` ; un `.ic` **absent** est
  toléré (pas d'échec). 8/8 `.ic` téléchargés, seuil 85 % appliqué.
* **Preuve CI** : `Instruction coverage: 88,93% (missed=32880, covered=264095)`
  — identique au monolithique. `BUILD SUCCESSFUL`.

=== 5. Local = Build, Tests = CI

Les shards sont gardés `onlyIf { System.getenv("CI") != null }` : en local
`./gradlew check` est inchangé (kover tire les shards, mais ils sont **SKIPPED** ;
un `.ic` absent est toléré). `check` conserve `functionalTest` + `cucumberTest` +
`nodeTest`. Les shards sont exclus de la découverte de `test` et `cucumberTest`
(`excludeTestsMatching("bakery.ci.shards.*")`).

== Limites honnêtes

* La cible **< 5 min** n'est atteinte qu'**au niveau des jobs de test** (le plus
  long : 4 m 27 s). Le **workflow complet** est à **5 m 55 s** : le plancher est
  imposé par le coût fixe **par runner** (setup GitHub ≈ 1 min + configuration /
  compilation Gradle ≈ 1 m 35 s) et par le job `coverage` (1 m 22 s) qui dépend de
  tous les autres. Passer à 3 shards functional réduirait la partie *tests* mais
  pas le coût fixe de compilation (payé par chaque runner) → gain marginal.
* `gradle/actions/setup-gradle@v4` (cache build) restauré (il existait dans
  l'ancien workflow) : gain mesuré sur Functional A (5 m 2 s → 4 m 18 s).

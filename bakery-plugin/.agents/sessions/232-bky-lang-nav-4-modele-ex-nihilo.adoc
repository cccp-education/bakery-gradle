== Contexte

Reprise bakery à la demande pilote (hook d'ouverture standard), méthodologie
baby-step DDD/TDD/BDD (unit → fonctionnel → cucumber) en agile software
craftmanship, commit/push autorisés en clôture.

Mission = quatrième US du cœur `BKY-LANG-NAV` (cadré S-228) : **rendre le modèle
ex-nihilo conforme** (D7). Un site scaffoldé par `generateSite` ne doit plus
« naître buggé » — le constat S-228 était net : `site-basic/templates/menu.thyme`
(et son frère `site/templates/menu.thyme`) émettaient un href **page-blind**
`'/' + ${lang.code} + '/'`, c'est-à-dire un retour à l'accueil de la langue.

== Le problème de design (note S-230 conciliée)

NAV-2 injecte un lien **par langue** dans un fragment (le renderer connaît la
langue cible et la langue courante). Le **modèle**, lui, est copié *verbatim* par
`generateSite` et utilise un **seul `th:each` sur `${supportedLanguages}`**
partagé par toutes les pages de toutes les langues : il n'y a pas de « page
courante » ni de « langue cible » à l'injection. L'expression doit donc lire
`lang.code` (cible) et `config.site_language` (courante) **au bake**.

Conciliation actée : la règle reste unique (`LangSwitchPath`), projetée sur une
*boucle* par un second frère symbolique `thymeleafEachHref(defaultLang)`.

== Livré — BKY-LANG-NAV-4

=== 1. `LangSwitchPath.thymeleafEachHref` — frère symbolique dynamique (DDD)

Génère l'expression `th:href` à quatre branches, évaluée **par itération** :

[source,kotlin]
----
fun thymeleafEachHref(defaultLang: String): String
// ${lang.code == config.site_language
//    ? content.uri.substring(content.uri.lastIndexOf('/') + 1)          // self
//    : (config.site_language == '<default>'
//       ? content.rootpath + lang.code + '/' + content.uri              // défaut → non-défaut
//       : (lang.code == '<default>'
//          ? '../' + content.rootpath + content.uri                     // non-défaut → défaut
//          : '../' + content.rootpath + lang.code + '/' + content.uri))} // non-défaut → non-défaut
----

La projection est **testée par évaluation réelle** : `LangSwitchPathEachHrefTest`
rejoue **11 des 14 vecteurs partagés** (`lang-switch-path-vectors.json`) via le
`TemplateEngine` — la même fixture que la règle pure (NAV-1) et l'hôte JS (NAV-3).
Preuve anti split-brain D3 étendue au troisième hôte.

=== 2. `LangSwitchModelGuard` — garde de conformité du modèle (DDD)

Objet pur (chaîne → verdict, zéro I/O). Vérifie que le sélecteur du modèle est
**page-aware** et pas seulement *présent* :

* `missing-selector` — pas de `language-switcher-container` / pas de `lang-option` ;
* `missing-data-lang` — l'option n'expose pas le contrat JS (D4) ;
* `page-blind-href` — href absolu `'/' + lang.code + '/'` (le bug S-228) ;
* `missing-page-awareness` — l'expression ne lit pas `content.uri`.

=== 3. Modèle corrigé (les deux arbres)

`site-basic/templates/menu.thyme` **et** `site/templates/menu.thyme` : l'ancre
devient `class="dropdown-item lang-option"` et `th:href` porte **exactement**
l'expression générée par la règle (pinnée byte-à-byte contre le modèle — D3),
remplaçant `'/' + ${lang.code} + '/'`.

== Limitation connue (honnêteté)

L'expression du **modèle** embarque `'fr'` comme langue par défaut (le générateur
`thymeleafEachHref(defaultLang)` est, lui, paramétré et testé). Le modèle étant
copié *verbatim*, il ne peut pas lire une langue par défaut configurable :
aucune clé `config.default_language` n'est injectée aujourd'hui. Pour un site
scaffoldé par `generateSite`, la langue par défaut est bien `fr` (défaut de
`SiteConfiguration`), donc la conformité est effective dans le cas nominal. Un
`config.default_language` injectable (et un `th:each` paramétré) est noté comme
suite possible — cf. NAV-5.

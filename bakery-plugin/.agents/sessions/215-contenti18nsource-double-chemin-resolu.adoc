== Mission

Le bug P3 (documenté S-207 : workaround `blog/2026`, observe pendant le
dogfooding MASS-5) : passer `--contentI18nSource=content/blog/2026` quand
`site.yml` définit `srcPath: jbake` produisait un chemin source
`jbake/content/blog/2026` (résolution naïve `resolvePath(base, path)`), soit
un « répertoire source n'existe pas » — le dossier réel est `jbake/blog/2026`.
L'utilisateur a demandé la clôture de cet item S-215.

== Diagnostic RED (cause racine)

- `SiteConfiguration.resolvePaths` (`BakeryPlugin.kt:245-251`) rend `srcPath`
  **absolu** : `contentRoot = projectDir.resolve(srcPath).resolve.resolvePath(base, path)`.
- `MigrateContentI18nTask` prenait ce `contentRoot` absolu comme dossier
  source de la copie → `--contentI18nSource` déjà préfixé par `srcPath`
  (`content/blog`) doublait avec le `srcPath` (`jbake/content/blog`).
- Forme non-préfixée (`content/blog` + `srcPath: jbake`) restait correcte car
  la résolution tombait sur `jbake/content/blog` — le comportement documenté
  dans la feature 59 et le DSL `i18n { contentI18nSource }`.

== Implémentation

=== US-1 — `ContentSourcePathResolver` (domaine `bakery.i18n.path`)

Objet pur `internal`, 3 règles segment-aware (match par segments, jamais par
préfixe de chaîne — `jb` ≠ `jbake`) :

1. Chemin absolu → utilisé tel quel.
2. Chemin préfixé par les segments `srcPath` → `projectDir.resolve(sourceDir)`
   (sans doublement).
3. Sinon → `projectDir.resolve(srcPath).resolve(sourceDir)` (comportement
   historique préservé).

Rétro-compatibilité totale : `--contentI18nSource=content/blog` avec
`srcPath: jbake` marche toujours (règle 3) ; la nouvelle forme préfixée
`jbake/content/blog` est résolue sans doublement (règle 2). Le workaround
S-207 (`blog/2026`) devient inutile.

=== US-2 — wiring tâche + registrar

- `MigrateContentI18nTask` : nouvelle propriété `contentSrcPath: String?`
  + `resolveSourceDir()` câblé au resolver.
- `ContentTaskRegistrar` : dérive `contentSrcPath` **relatif au projectDir**
  (`contentRoot.relativeTo(project.projectDir).path` si `contentRoot`
  démarre par `project.projectDir`, sinon `null`) — le registrar connaît la
  vérité (le `contentRoot` résolu par `resolvePaths`), la tâche consomme le
  chemin source relatif.

=== Note sémantique copie

L'arbre copié est préservé **relatif au dossier source** : un dossier source
`content/blog` (relatif projectDir) aboutit à
`build/i18n-en/en/2020/0016_simple_post.adoc` (assertions FT).

== Décisions

1. *Le registrar est la source de vérité du chemin relatif* — `resolvePaths`
   produit un `contentRoot` absolu (nécessaire par ailleurs), le registrar
   re-derive le `contentSrcPath` relatif au projectDir pour la tâche.
2. *Resolver pur segment-aware* (et non `startsWith` naive) — évite les
   faux positifs de préfixe partiel ; conforme au pattern DDD object pur
   (`bakery.i18n.path`, 23e domaine).
3. *Rétro-compatibilité non-brisée* — forme non-préfixée historique inchangée
   (règle 3), forme préfixée désormais correcte (règle 2), absolu tel quel
   (règle 1). Aucune suppression du workaround documenté nécessaire en CI.
4. *Runner dédié pour feature 63* — pattern S-082 (runner standalone +
   `CucumberTaskSpec`), cohérent avec features 55/60/62 ; le runner standard
   reste `@pipeline-contracts`.

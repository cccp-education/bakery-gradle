== Ce qui a été livré

=== US-1 — le payload survit au déploiement

* `bakery.deploy.DeployPayload` (pur) : racine, exclusions (`.git`, `CNAME`,
  `**/*.bak`, extras), listing **ordonné**, SHA-256 par contenu, digest
  `(chemin, hash)` — insensible à l'ordre, sensible à un octet et à un renommage.
* `bakery.deploy.DeployTarget` (`GitPages` | `Netlify`) et `DeployOutcome`
  (`Deployed` | `Skipped` | `Failed`) — le transport Git est *enveloppé*, pas
  réécrit.
* **Deux suppressions retirées** (constat C4 corrigé) :
  `FileSystemManager.copyBakedFilesToRepo` ne supprime plus `bakeDir` après
  copie, et `GitService.cleanupPublicationArtifacts` ne supprime plus que le
  dépôt temporaire. Deux cibles lisent donc le même arbre dans le même build.
* Tests : `DeployPayloadTest` (9 UT), `GitServiceTest` (payload conservé après
  push), `FileSystemManagerTest` (bakeDir conservé).

=== US-2 — configuration + garde

* `bakery.netlify.NetlifyConfig` (+ `NetlifyDeployOptions`, `NetlifyTomlOptions`),
  `SiteConfiguration.netlify` (section optionnelle, `null` = aucune tâche).
* `NetlifyDsl` + `BakeryExtension.netlify { … }`.
* `NetlifyConfigResolver` : cascade CLI > gradle.properties > DSL > site.yml >
  défauts via `ConfigResolver` (chaque couche testée).
* `VerifyConfigurationMappingTask` : `pushPage.from/to` non requis quand
  `netlify.siteId` est configuré ; le résumé expose `siteId`/`tokenEnv` et jamais
  un jeton.
* Tests : `NetlifyConfigResolverTest` (5 UT), `VerifyConfigurationMappingNetlifyTest`
  (3 UT).

=== US-3 — plan pur + économie d'encre

* `NetlifyDeployPlan`, `NetlifyDecision` (`Deploy` | `Skip` | `Fail`),
  `NetlifyPlanner` : site id vide = échec, payload vide = échec, digest identique
  pour le même site = `Skip` (sauf `force`), autre site = deploy, `dryRun`
  n'uploade jamais.
* `NetlifyDeploymentRecord` + `NetlifyDeploymentRecordStore` (JSON
  `last-deploy.json`, fichier illisible = « pas de précédent », dégradation
  silencieuse).
* Tests : `NetlifyPlannerTest` (6 UT).

=== US-4 — port + adapter + client API

* `NetlifyHttp` (port), `JavaNetlifyHttp` (`java.net.http`, en-tête
  `Authorization` seulement si jeton non vide), `NetlifyApiClient` (création de
  déploiement, polling borné, mapping `401`/`404`/`429`/`4xx`/`5xx`, messages
  sans jeton).
* Décision : **pas de retry POST** (non idempotent — un `5xx` peut avoir créé le
  déploiement) ; le poll GET est borné et injectable (`sleeper`) pour les tests.
* Tests : `NetlifyApiClientTest` (6 UT).

=== US-5 — tâches + câblage

* `GenerateNetlifyTomlTask` : `netlify.toml`, `_headers`, `_redirects`

* `BakeryPlugin` : résolution de la config et enregistrement dans le pipeline
  complet uniquement.

== Itération CI (run `44225748648` — 3 échecs corrigés)

Le premier push a révélé trois défauts réels (BDD verts, 15/18 jobs verts) :

. **`DeployPayloadTest` — exclusion `.git` à toute profondeur.** Le glob
  `.git/**` n'ancrait que la racine ; `BASE_EXCLUDES` devient `**/.git/**`
  (racine + sous-répertoires).
. **`NetlifyConfigResolverTest` — sémantique de cascade.** Le test attendait
  qu'un booléen DSL égal au défaut surcharge le YAML ; `ConfigResolver` considère
  qu'un booléen égal au défaut n'est pas « explicitement posé ». Test corrigé
  (valeur DSL non-défaut gagne) + test explicite de la règle
  (« un DSL égal au défaut ne surcharge pas le YAML »).
. **`NetlifyFunctionalTest` — le skip ne skippait pas.** `last-deploy.json` était
  déclaré `@OutputFile` : Gradle **nettoie les sorties obsolètes** avant la
  première exécution et supprimait le record → plan `Deploy` → échec « token
  empty » (25 tests, 1 échec). Le record est désormais `@LocalState` (état, pas
  sortie). Reproduit et vérifié en composite locale (`includeBuild` du plugin) :
  `[netlify] skipped — payload unchanged since the last deployment`.

Re-gates (Local = Build) : compiles ×3, `assemble`, `validatePlugins`,
`ktlintCheck` VERTS. **Preuve CI définitive** (commit `1a60ec41`) : run
`44226716284` **VERT** (18/18 jobs, 0 échec) + `Publish website`
`44226716350` **VERT**.

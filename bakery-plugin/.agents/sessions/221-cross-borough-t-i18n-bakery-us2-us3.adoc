== Mission

Mission pilote : « T-I18N-BAKERY » — les US-2 (wiring build talaria) et US-3 (retrait du
harness node) restaient bloquées par l'EPIC bakery `BKY-I18N-JS`, clos S-220. Demande

== Audit d'ouverture — où vit la config du pool LLM (US-2)

`translateI18nClient` n'appelle le LLM que si `bakery { ia { enabled = true } }` est posé
là où le plugin est appliqué. Or talaria n'applique pas bakery : c'est le **runner-gradle
(N3) partagé** qui l'applique. Mesure des 3 chemins de configuration :

. `-Pia.enabled=true` — **documenté** (`ValidateFirebaseConfigTask.kt:34`) mais **jamais
  lu** (`grep '"ia\.' src/main` = 0) : documentation morte.
. `site.yml → ollama:` (`contracts.i18n.OllamaConfig`) — **parsé** (`SiteConfiguration.kt:59`,
  affiché par `verifyConfigurationMapping`) mais **ignoré** par `iaConfig`.
. DSL `bakery { ia { … } }` — seul chemin réel, inaccessible depuis talaria.

**Décision (recommandation agent, validation pilote)** : option C — dériver `iaConfig` de
`site.yml → ollama:`. Résolution **locale** dans `registerTranslateI18nClientTask` (périmètre
US-2 strict, zéro impact cross-borough sur `BakeryPlugin`), portée par un **domaine pur**.

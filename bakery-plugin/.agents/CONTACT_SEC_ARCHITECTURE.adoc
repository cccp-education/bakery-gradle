=== 1.2 Défenses déjà en place (Session 034)

[cols="2,3,3"]
|===
| Couche | Client (contact.js) | Serveur (Apps Script)

| Honeypot
| Champ caché `hp_name` ; si rempli → faux succès silencieux
| Champ `hp_name` non vide → rejet silencieux

| Timing anti-bot
| `ts_render` = `Date.now()` au DOMContentLoaded
| Soumission < 2.5s après render → rejet

| Validation email
| Regex `^[^\s@]+@[^\s@]+\.[^\s@]+$`
| Regex identique côté serveur

| Rate limit
| — (aucun, coté client impossible)
| 3/h par email + cap 30/jour (CacheService)
|===

=== 1.3 Point faible structurel (motivation de l'EPIC)

*Le POST `no-cors` vers l'endpoint Apps Script est directement rejouable.* Un bot
ignore le JS, appelle `<script-endpoint>/exec` en brut avec `hp_name=""` +
`ts_render=Date.now()`. Les 4 défenses actuelles filtrent uniquement les bots
naïfs. Aucune vérification serveur réelle (CAPTCHA/vérif humaine) n'existe.

**Racine** : le site est *statique* — aucun backend propre pour vérifier une
preuve. Le seul "backend" disponible est l'endpoint Apps Script lui-même
(`UrlFetchApp` permet d'appeler des API externes depuis le script).

== 4. Les 6 améliorations — plan détaillé

=== 4.1 Turnstile (Cloudflare) — vérification serveur réelle — **PRIORITÉ 1**

Le seul moyen d'avoir une vérification humaine *réelle* sur un site statique.
`sitekey` est public (JS), `secret` vit dans le script Apps Script (jamais exposé).

**Flux** :
----
Navigateur                       Apps Script                     Cloudflare
  │ widget Turnstile (invisible)   │                              │
  │ → token                        │                              │
  │ POST {token, ...}  ──────────▶ │ doPost                        │
  │                               │ UrlFetchApp POST              │
  │                               │ challenges.cloudflare.com     │
  │                               │ /turnstile/v0/siteverify      │
  │                               │   {secret, response=token}    │
  │                               │ ◀── {success: true/false}     │
  │ ◀── 400 si invalid             │                              │
----

* **Client** : charger `https://challenges.cloudflare.com/turnstile/v0/api.js` dans `footer.thyme` (attribut `data-sitekey`), écouter `window.turnstile.getResponse()` à la soumission, injecter `cf_turnstile_token` dans le payload.
* **Serveur (contrat)** : `UrlFetchApp.fetch("https://challenges.cloudflare.com/turnstile/v0/siteverify", {method:"POST", payload:{secret, response}, muteHttpExceptions:true})` → si `success != true` → 400.
* **Bénéfice** : bloque ~100% du spam automatisé. Gratuit illimité, privacy-friendly, invisible pour l'utilisateur.
* **Prérequis opérateur** : compte Cloudflare → domaine cheroliv.com → Turnstile → sitekey+secret.
* **Tests bakery** : stub `turnstile.placeholder.js` (token factice `0xTEST`), unit test du renderer (div + data-sitekey), functional test de la config (`siteKey` requis si `turnstile.enabled`).

=== 4.2 Rate limit par empreinte + cap global — renforcer l'existant

Apps Script n'a **pas l'IP client** (impossible). À la place :
* **Clé de cache** = `sha256(fingerprint + email)` via `CacheService` (TTL 1h), en plus de l'email seul.
* **Fingerprint client** : hash(UA + screen + language + canvas signature partielle) calculé dans `contact.js`, envoyé comme `fp` (déjà haché, pas de donnée brute).
* **Cap global quotidien** : compteur total dans `CacheService` (TTL 24h), ex. 50/jour toutes origines → anti-flood massif.
* **Tests** : domaine pur `RateLimiter` (allow/deny/expiry), unit test fingerprint hashing, functional test cap global.

=== 4.3 Token anti-rejeu à usage unique

Neutralise le rejeu pur du payload capturé (un bot qui répète un POST valide).
* **Client** : `GET <endpoint>?action=new-session` au chargement → reçoit `session_token` (CacheService, TTL 10min).
* **Soumission** : inclut `session_token` ; le script le consomme (get + remove → usage unique).
* **Serveur (contrat)** : si token absent/expiré/déjà consommé → 400.
* **Tests** : domaine pur `SessionTokenManager` (issue/validate/consume/expiry/double-consume refusé).

=== 4.4 Preuve de travail côté client (PoW) — sans tiers

Filtre les bots à grande échelle sans dépendance externe.
* **Client** : le site fournit `pow_challenge` (généré par le script ou en dur dans la config) ; `contact.js` trouve `pow_nonce` tel que `sha256(challenge + nonce)` commence par N zéros (~200ms CPU humain, coûteux en masse).
* **Serveur (contrat)** : vérifie le nonce avant traitement.
* **Tests** : domaine pur `PowVerifier` (difficulté N, nonce valide/invalide, idempotent challenge).

=== 4.5 Heuristiques de contenu (antispam classique)

* ≥3 URLs dans le message → rejet (les vraies demandes de contact ont rarement 3 liens).
* message == subject (copie) → rejet.
* Domaine email jetable → rejet (petite denylist embarquée : mailinator, guerrillamail, 10minutemail, etc.).
* Texte incohérent : ratio caractères non-Latin > 50% ou pas d'espace (gibberish) → rejet.
* **Tests** : domaine pur `ContentHeuristics` (detectUrls, detectGibberish, isDisposableDomain, isDuplicateSubject).

=== 4.6 Firestore rules renforcées

* Règles actuelles : `create` sur `contact_messages` only, typage string, bornes tailles.
* Renforcer : exiger `created_at == request.time` (serverTimestamp), interdire les champs inconnus (whitelist), cap longueur message (ex. 4000 chars), rejeter si `hp_name` non vide (double couche avec Apps Script).
* **Génération** : la tâche bakery `scaffoldContactSec` produit `firestore.rules` de référence (paramétré par `ContactSecConfig`).
* **Tests** : unit test du générateur de règles (template → sortie attendue, scénarios create valide/invalide).

== 5. Procédure opérateur (reprise en main du runtime)

Quand un site consomme le scaffold bakery, l'opérateur doit :
. Créer un projet Firebase (région europe-west1) + App Web → récupérer config
. Publier les `firestore.rules` générées (console ou `firebase deploy`)
. Créer le script Apps Script (Apps Script → Nouveau projet) :
  * coller le code de référence généré (§4 — Turnstile siteverify, RateLimiter, SessionTokenManager, PowVerifier, ContentHeuristics, MailApp)
  * `secret` Turnstile en propriété script (`PropertiesService`) ou constante non commitée
  * Déployer → "Nouveau déploiement" → "Exécuter en tant que : moi" → "Qui a accès : Tout le monde" → copier l'URL `/exec`
. Renseigner `contact.endpointUrl` + `contact.turnstile.siteKey` dans `site.yml`
. Test manuel complet (succès, honeypot, timing, email invalide, rejeu token, PoW invalide, rate limit)

**Backup** : le script Apps Script actuel de cheroliv.com (endpoint
`<script-endpoint>`, version réelle dans le repo privé `office/`) est la
référence runtime — à sauvegarder avant toute modification (pas de git côté
Apps Script, export .gs manuel).

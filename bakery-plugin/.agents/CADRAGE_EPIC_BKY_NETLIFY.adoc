== Demande pilote

Ajouter **une autre cible de déploiement** — Netlify — pour le site statique
produit par bakery, sans casser la cible historique (push Git → GitHub Pages).
Cadrer l'EPIC dans le backlog.

Le déploiement actuel n'est pas « GitHub Pages » en tant que tel : c'est un
**push Git forcé** vers un dépôt/branche servis par Pages. Netlify est le
premier **fournisseur non-Git** du pipeline ; il force donc à nommer la notion
de *cible* (aujourd'hui implicite) et à découpler le *payload* de son
*transport*.

== Décisions

=== D1 — Cible **additive**, jamais un remplacement

`deploySite` (push Git → Pages) et `pushCiMirror` gardent leur sémantique ;
`publishSite` est **inchangée** (contrat consommé par 4 workflows `office` et par
`runner-gradle`). Nouvelles tâches :

* `generateNetlifyToml` (groupe `generate`),
* `deployNetlify` (groupe `deploy`),
* `publishSiteNetlify` (agrégat : `bake` + `deployNetlify` + `accessibilityAudit`),
* `publishSiteAll` (agrégat optionnel : `publishSite` + `publishSiteNetlify`).

Un site sans section `netlify:` ne voit **aucune** tâche nouvelle
(enregistrement conditionnel, patron `DnsTaskRegistrar`).

=== D2 — Déploiement **direct par API** comme mécanisme primaire

Bakery a déjà produit l'arbre (bake + variantes + pagefind) : laisser Netlify
re-builder dupliquerait le travail et pourrait diverger (versions Node/JRuby,
contenu non commité). Le déploiement primaire est donc un **envoi du payload**
à l'API Netlify, adressé par contenu (Netlify déduplique les fichiers
identiques, l'envoi reste bon marché).

Le mode « Netlify construit depuis un dépôt Git » (D11 + `netlify.toml`) est
**secondaire**, opt-in, et n'entre pas dans le chemin par défaut.

=== D3 — Contrat de cible explicite, sans réécriture du transport Git

Domaine `bakery.deploy` : `DeployTarget` (sealed `GitPages` | `Netlify`),
`DeployOutcome` (sealed `Deployed(url, deployId)` | `Skipped(reason)` |
`Failed(message)`), `DeployPayload`. Le chemin Git est **enveloppé** (US-1),
pas réécrit : `GitService` garde son comportement observable.

=== D4 — Le payload survit au déploiement (US-1, prérequis dur)

`GitService.pushPages` ne supprime plus que son **dépôt temporaire** ; le répertoire
baké reste sur disque. Deux cibles peuvent ainsi consommer le même arbre, et un
smoke post-déploiement peut lire ce qui a été publié. La suppression du payload
était un artefact de nettoyage, pas une garantie : elle est retirée avec un test
de non-régression explicite (déploiement deux fois = arbre présent, second envoi
identique).

=== D5 — Une seule définition du payload

`DeployPayload` (objet pur) : racine `build/<bake.destDirPath>`, exclusions
(`CNAME`, `.git/**`, `**/*.bak`), listing **ordonné** et déterministe, digest
SHA-256 sur `(chemin relatif, sha256(contenu))`. Les deux cibles partagent cette
définition ; aucun filtre spécifique n'est dupliqué dans les tâches.

=== D6 — Le jeton n'est jamais une valeur de configuration

`NetlifyConfig` porte le **nom** de la variable (`tokenEnv: NETLIFY_AUTH_TOKEN`),
jamais le jeton. Résolution : variable d'environnement uniquement (jamais une
propriété Gradle, qui apparaîtrait dans `ps`/les logs). La tâche porte le jeton en
`@Internal` (jamais haché, jamais mis en cache), `toString()` masqué, aucune ligne
de journal ne le contient. Section présente + jeton absent ⇒ **échec explicite**
(jamais un skip silencieux qui ferait un faux vert).

=== D7 — Économie d'Encre : digest avant réseau

`build/bakery/netlify/last-deploy.json` conserve `siteId`, `digest`, `deployId`,
`deployUrl`, horodatage. Digest identique + `--netlifyForce` absent ⇒
`Skipped("unchanged")`, **zéro appel réseau**. On ne compte pas sur la
déduplication de Netlify pour éviter un envoi.

=== D8 — Pas de dry-run par défaut ; un dry-run explicite et utile

Contrairement à `provisionDns` (mutation d'une zone partagée), un déploiement est
une action **explicitement demandée**. `--netlifyDryRun` imprime le plan
(site, nombre de fichiers, octets, digest, exclusions) et n'effectue aucun appel.
En CI sans jeton, la preuve reste le test fonctionnel sur stub loopback — jamais
un vrai déploiement.

=== D9 — Preuve du déploiement

La tâche imprime `deployId` + `deployUrl`/`ssl_url` et écrit le rapport
`build/bakery/netlify/deploy.json`. Un smoke opt-in (`--netlifySmokeUrl`) vérifie
que l'hôte vivant sert un marqueur du bake (même discipline que le smoke
post-déploiement talaria). En CI, ce smoke n'est activé que par le dogfooding.

=== D10 — Frontière : bakery publie, ne provisionne pas

Hors périmètre : création du site Netlify, domaine/HTTPS/certificats, variables
d'environnement Netlify, fonctions/edge, analytics, rollback d'interface,
provisionnement DNS Netlify (le domaine `dns:` reste OVH, BKY-DNS). `siteId` est
fourni par le pilote.

=== D11 — `netlify.toml` est une sortie, pas une source de vérité

`generateNetlifyToml` écrit un `netlify.toml` déterministe (publish dir, redirections
404, en-têtes de sécurité de base, `[[headers]]` pour les assets). Il sert au mode
secondaire « Netlify build from git » et documente le site ; il n'est **pas**
utilisé par l'envoi direct (qui transporte l'arbre déjà baké).

=== D12 — Cascade de configuration honorée et testée

`netlify` suit la cascade sur les champs non secrets : `site.yml` < DSL <
`gradle.properties` (`bakery.netlify.*`) < CLI (`-Pbakery.netlify.*`), via
`ConfigResolver` (comme `theme`/`analytics`). Le jeton fait exception (D6). Chaque
couche est couverte par un test : aucune prétention non prouvée (leçon C12).

=== D13 — Parité multi-langue et recherche

Le payload Netlify est l'arbre post-`bakeVariants`/`pagefind` : `{lang}/` et
`pagefind/` présents quand le site les déclare. Un test le verrouille ; aucune
cible ne re-bake son propre arbre.

=== D14 — Aucune dépendance d'exécution nouvelle

`java.net.http.HttpClient` (déjà utilisé par `dns/JavaOvhHttp`), `java.util.zip`
(JDK), Jackson (déjà présent). Pas de SDK Netlify, pas de client HTTP tiers.

=== D15 — Pas de course entre cibles

`deployNetlify.mustRunAfter("deploySite")` (douce) et exclusion systématique de
`CNAME` : jamais deux écritures concurrentes du même répertoire. Un seul site
`site.yml` décrit une seule identité de publication.

== Contrat de configuration

[source,yaml]
----
# site.yml — section optionnelle ; absente = aucune tâche Netlify
netlify:
  siteId: "xxxxxxxx-xxxx-xxxx-xxxx-xxxxxxxxxxxx"   # jamais un secret
  tokenEnv: NETLIFY_AUTH_TOKEN                      # NOM de la variable, jamais le jeton
  deploy:
    exclude: ["CNAME", "**/*.bak"]                  # D5 (CNAME toujours exclu)
    message: "bakery deploy"
  verifyUrl: "https://talaria.school/"              # smoke opt-in (D9)
  toml:                                             # D11 (mode secondaire)
    enabled: false
    publishDir: "bakery-plugin/build/site"
----

== Frontière

* **Bakery** : payload, plan, digest, adapter API, tâche, `netlify.toml`, gardes,
rapport.
* **Consommateur (site)** : `site.yml` (`siteId`, `tokenEnv`, options), jeton en
secret CI, choix de la cible, smoke du domaine.
* **`office` / runner N3** : injection du secret et appel de `publishSiteNetlify`
(si un site l'adopte) ; aucune logique de déploiement dupliquée.

== Risques et mitigations

[cols="1,3,4", options="header"]
|===
| # | Risque | Mitigation

| R1
| Retirer la suppression du payload (US-1) surprend un consommateur qui comptait
sur le nettoyage disque. | Seul le dépôt temporaire reste supprimé ; FT explicite ;
rapport de session ; aucun contrat public changé (le répertoire est sous `build/`).

| R2
| Dérive de l'API Netlify (endpoints de déploiement). | Un seul adapter, endpoint
centralisé, tests de contrat sur fixtures, erreurs explicites (`404`/`410`).

| R3
| Fuite du jeton. | D6 (nom de variable, `@Internal`, redaction, jamais de log) +
`grep` de fin de session + test de redaction.

| R4
| Faux vert : section présente, jeton absent, tâche qui « skip ». | Échec explicite
obligatoire (D6) ; seul le dry-run est silencieux sur le réseau.

| R5
| Payload volumineux (22 langues) : temps d'envoi / mémoire. | ZIP en flux,
`--netlifyDryRun` affiche octets/fichiers avant tout envoi, déduplication par
contenu côté Netlify.

| R6
| Duplication de logique entre `deploySite` et `deployNetlify`. | `DeployPayload`
unique (D5) ; `DeployOutcome` unique ; aucun filtre propre à une tâche.

| R7
| Divergence « Netlify build from git » vs envoi direct. | D2 : l'envoi direct est
le chemin par défaut ; `netlify.toml` est secondaire et documenté comme tel.

| R8
| Prétendre une cascade de configuration non implémentée (leçon C12). | D12 :
chaque couche testée, ou pas de prétention.

| R9
| Smoke du domaine trompé par un cache/CDN. | Marqueur de build unique ou
`?cachebust` ; smoke opt-in, jamais dans le chemin CI standard.

| R10
| Extension de périmètre (site, DNS, fonctions). | D10 : liste explicite des
non-objectifs ; toute extension = EPIC séparé.
